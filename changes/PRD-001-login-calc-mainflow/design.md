# 技术设计：PRD-001 · 平台接入与测算主链路

## 上下文

- **当前状态**：目标仓库 `D:/1_code/investment-research-agent` 几乎为空（仅 `.git`/`.claude`）。参考项目 etrader-agent-nx **仅作前端设计借鉴**：
  - 前端设计体系 `agent-frontend/src/design-system/`（XC 玄策：`--xc-*` token、`.xc-*`、Element Plus 覆盖、CHARTS.md），及其通用框架层写法（axios 请求实例、布局、通用组件、svg-icon、nprogress），可作为本系统前端搭建的**风格与结构参考**。
  - `src/components/fullscreen-chat/`（对话 UI + 图表/报告块内联渲染）可作为对话首页与结果三模块的**交互参考**。
  - **注意（PRD §3 明确）**：trader **仅作前端设计借鉴，其后端业务/鉴权代码不作为本系统参考**；trader 后续也会改造为对接统一平台的子平台。
- **接入基调（PRD 2026-07-04 变更）**：本系统是**统一平台的子应用**（同域）。登录/注册/验证码/用户管理/RBAC **全部由统一平台首页负责，本系统不做**。用户在平台首页完成统一登录后跳转承接进入本系统对话首页。身份透传**已定原则**：平台/网关将用户标识**注入请求头**，本系统后端**直接信任读取 `user_id`/`username`**（仅用于快照 `conversation` 归属），**不自建登录、不做 token 二次校验、不依赖任何外部登录态存储**。确切 header 字段名与平台跳转入口 URL 待与平台约定（挂账 #8，不阻塞，先用可配默认值）。
- **约束条件**：前端视觉与 trader/平台统一（XC 玄策设计体系）；后端采用**团队统一栈**（FastAPI + 异步 SQLAlchemy MySQL + Nacos，仅框架选型一致）；配置分层（前端 `.env` 仅网关基地址，后端走 Nacos）；飞书为唯一权威计算器、系统不重写公式、只读写接口区（方案A）；MySQL 新库 `ir_agent`；网关前缀 `/ir`。
- **利益相关者**：内部投研用户（3–5 人，经平台承接进入）、统一平台/网关团队（登录鉴权与 header 注入、跳转入口）、业务方（黄安琦，负责飞书接口区与桥接公式）、平台运维（Nacos/网关/MySQL）。

## 目标

- 以最小成本承接平台跳转、落地对话首页，后端从请求头读取身份用于快照归属，**不实现任何登录/用户/权限**。
- 前端全新工程，接入 XC 玄策设计体系与通用框架层，视觉与平台统一。
- 后端团队统一栈，落地飞书方案A 测算执行链路（状态机/轮询/智能重试）与 7 类快照，历史结果脱离飞书副本可用。
- 结果三模块（基本信息/财务指标/进阶图形）在对话内 inline 展示，参数可 inline 调整并多版本重算。
- 历史会话可按当前平台用户列出、手动回放和软删除，回放结果只读 report_snapshot。

## 非目标

- **不实现登录页、注册、图形验证码、用户管理、角色/权限（RBAC）、token 二次校验、SSO 会话管理**（由统一平台负责）。
- 不实现报告模块本体、PDF 导出、中台 Tool 封装、地图/政策模块（仅占位）。
- 不重写储能测算公式、不重写电价库"96点→均价"算法（仅引用）。
- 不参考 trader 后端业务/鉴权代码（仅前端设计借鉴）。

## 决策

### 决策 D1：前端为全新工程，接入 XC 设计体系 + 通用框架层

- **选择**：在 `agent-frontend/` 新建 Vite+Vue3 工程，移植 `src/design-system/`（XC 玄策）并借鉴 trader 前端的通用框架层写法（axios 请求实例、布局、通用组件、svg-icon、nprogress）搭建本系统骨架；**无独立登录页、无登录路由守卫、无用户/权限模块**，默认落地页即对话首页。
- **理由**：PRD 明确前端对齐 trader 视觉（XC 体系），trader 仅作前端设计借鉴；阶段0 无登录，前端骨架大幅简化。
- **考虑的替代方案**：①整仓 fork etrader（带入交易业务与登录冗余，与"平台子应用、无登录"定位不符）；②纯手写不借鉴（风格易漂移、重复造轮子）。折中取"新工程 + 设计体系移植 + 框架层借鉴"。

### 决策 D2：不做登录，承接平台身份注入（读 header）

- **选择**：本系统**不实现**登录/注册/验证码/用户/权限。承接统一平台跳转入口 URL 落地对话首页；后端以轻量中间件/依赖从请求头读取 `user_id`/`username`（header 字段名经 Nacos/env 可配，默认待与平台约定），注入 `request.state` 供快照 `conversation` 归属；**直接信任、不做 token 二次校验、不依赖外部登录态存储**。header 缺失按可配策略（开发放行匿名占位 / 生产按约定字段处理）。
- **理由**：PRD 2026-07-04 变更明确"登录/用户/权限交由平台，身份经平台/网关注入 header、后端直接信任读取，只取 user_id/username 供归属"。同域子应用，无需自建任何登录态。
- **考虑的替代方案**：①自建登录/令牌（上一版方案，已被 PRD 变更废弃）；②对接平台做 token 二次校验（PRD 明确不做，增加与平台耦合与复杂度）。
- **对接要点**：确切 header 字段名与跳转入口 URL 待平台约定（挂账 #8）；字段名可配以便零改码对接；不落地任何密码/令牌/用户表。

### 决策 D3：后端采用团队统一栈 FastAPI（框架一致，不抄 trader 代码）

- **选择**：`create_app()` 应用工厂（CORS → 请求日志 → 平台身份读取中间件）、Nacos 配置装载（data_id=`{app.name}-{profile}.yml`，本地降级）、异步 SQLAlchemy 会话依赖、`{code,msg,data}` 响应壳与四类异常处理器、loguru 日志，集中 `register_routers()`。仅**框架选型**与团队一致，实现自研，不复制 trader 的业务/鉴权代码。
- **理由**：团队统一栈，降低认知与运维成本；无 `AuthMiddleware`/`TokenService`，改为轻量身份读取中间件（见 D2）。
- **考虑的替代方案**：轻量 Flask/裸 FastAPI 无 Nacos（偏离团队约定，配置无法统一治理）。

### 决策 D4：飞书集成走方案A 独立接口区 + 独立客户端

- **选择**：新增 `feishu_client`（httpx + tenacity，配置/凭证来自 Nacos），只读写 `API_INPUT/API_OUTPUT/API_META` 三 sheet 指定单元格，含超时/重试/错误分类。
- **理由**：系统契约与模型解耦，模型单元格挪动只断业务桥接公式（Excel 自愈/显式 #REF! 可见/业务自修），系统不发版。
- **考虑的替代方案**：直接读写模型单元格（脆弱、模型一动即断且难自愈）。方案A 为 PRD 既定。

### 决策 D5：测算执行采用"异步任务 + 前端轮询任务状态"

- **选择**：前端发起测算得到 `task_id`，后端以状态机异步执行（copying→…→completed），并对飞书 `API_META` 做内部轮询（默认 3s 间隔 / 10s 总超时，Nacos 可配）；前端对**本系统任务状态**接口轮询直至 completed/failed，再拉结果三模块。智能重试在后端状态机内完成（复用同副本，最多 3 次）。
- **理由**：飞书重算耗时不确定，单请求同步阻塞易触发网关/浏览器超时；异步任务 + 状态轮询解耦等待，前端可展示"测算中"。3–5 人低频，无需复杂队列。
- **考虑的替代方案**：①单请求同步阻塞直到出结果（实现简单但超时风险高、体验差）；②引入消息队列/独立 worker（一阶段过重）。折中采用应用内异步任务（asyncio task，必要时 apscheduler 兜底恢复，参考 trader 的恢复任务模式）。

### 决策 D6：7 类快照落 MySQL `ir_agent`，JSON 字段存储

- **选择**：`conversation`、`message_snapshot`、`calculation_task`、`input_snapshot`、`data_snapshot`、`feishu_io_snapshot`、`report_snapshot` 七表，复杂结构以 JSON 列存储；`report_snapshot` 含环形图/折线图底层数值，作为历史展示唯一数据源；Alembic 管理迁移。
- **理由**：每次测算独立不覆盖、可追溯；report_snapshot 脱离飞书副本长期可用（满足"副本清理后历史仍可看"）。
- **考虑的替代方案**：仅存飞书副本链接（副本被清理即丢失历史，违反 US-1.4 场景4）。

### 决策 D7：对话与结果三模块借鉴 fullscreen-chat 模式

- **选择**：借鉴 trader `src/components/fullscreen-chat` 的消息流 + 内联块（图表/报告块）交互，构建首页对话视图与"结果三模块"内联卡片；环形图/折线图用 ECharts，配色遵循 `design-system/CHARTS.md`（红涨绿跌硬约束）。
- **理由**：借鉴成熟对话/图表交互，减少自研；风格天然对齐 XC。
- **考虑的替代方案**：从零写对话与图表容器（重复劳动、风格易漂移）。

### 决策 D8：参数字典以结构化文件承载，运行时下发

- **选择**：参数字典（F=1 + 表2 收敛、含来源/默认/单位/类型/显示F/可调G/接口区单元格）以后端可版本化的 JSON/YAML 存储，运行时由后端接口向前端下发"可展示/可调/显隐"元数据；表2 取数由后端完成。
- **理由**：字典需业务逐项校对且会演进；与代码解耦便于维护；前端不硬编码参数集合。
- **考虑的替代方案**：前端硬编码参数表（业务一改就要发版）。

### 决策 D9：配置分层（前端 .env / 后端 Nacos）

- **选择**：前端 `.env.*` 仅 `VITE_APP_BASE_API`/`VITE_APP_TITLE`/`VITE_FAVICON`/`VITE_APP_ENV`；后端飞书凭证、轮询阈值、数据源、Redis、功能开关走 Nacos（区分 test/prod），本地降级。
- **理由**：与 trader/eTrader 一致，敏感配置不入前端与代码库。

### 决策 D10：历史会话手动回放、软删除与资源归属

- **选择**：左侧栏以“投资分析工作台”为功能导航大项，全部功能项之后用分隔线展示历史会话；页面进入/刷新只加载列表并保持欢迎页，点击后一次加载该会话固定顺序的消息、任务版本和 report_snapshot。会话通过“…”菜单二次确认软删除，在 `ir_conversation` 增加 `deleted_at`；列表过滤已删除会话，消息、任务及快照不级联删除。会话列表/详情/删除及任务状态/结果均以当前平台 `user_id` 做归属约束，越权统一返回 404。
- **理由**：数据库已持久化完整回放数据，但缺少读取入口；手动打开避免刷新后意外进入旧项目。软删除保留测算审计与 report_snapshot 历史数据，也规避当前无 `ON DELETE CASCADE` 时 MySQL 与 SQLite 行为不一致的问题。404 不暴露其他用户资源是否存在。
- **考虑的替代方案**：①自动打开最近会话（违背欢迎页入口预期）；②永久硬删除（不可恢复且需维护多表删除顺序）；③数据库级级联删除（迁移重、误删影响大）。
- **报告扩展约束**：报告本体不在本轮实现；未来报告记录必须关联 `conversation_id + task_id + version`，历史会话详情可据此挂载报告历史。

### 决策 D11：参数覆盖与现货电价依赖重算

- **选择**：`POST /ir/calc/tasks` 增加受控 `param_overrides`，仅允许参数字典中 `g=1 + direction=input + writable=true` 的字段。前端提交当前完整面板值，后端以 input_snapshot 为版本基线完成冻结和比较。省份在同一会话永久锁定，换省必须新建会话。现货市场遵循 `switch_spot`；开关为0时不展示、不查库。开关为1时，后端比较【节点、容量、功率、日均充放电次数】：任一变化即忽略旧现货价格对并按最新参数查预计算表；均未变化则不查库，继承上一版本价格对并叠加本次手工修改。
- **理由**：现货价格由节点和 K（容量/功率/循环次数）共同决定，依赖变化后旧价格失效；依赖不变时重复查库会覆盖用户已确认的手工价格，也无法让 V3 正确继承 V2。判断必须在持有上一版本 input_snapshot 的后端完成，不能信任前端布尔标记。
- **考虑的替代方案**：①每次重算都查库（会覆盖手工调价）；②只要改过任一电价就永久不查库（节点/K变化后价格错误）；③由前端决定是否查库（刷新回放和恶意请求下不可靠）。
- **单位约束**：飞书底稿 D39/D40 已由用户确认采用元/kWh；现货预计算表保留元/MWh 原始值，`PrecomputeSpotPriceAlgo` 保留现有 `/1000` 输出元/kWh，参数字典现货字段已同步为元/kWh。本批次不得修改该换算与底稿映射。

## 风险与权衡

- **飞书 PoC（头号风险）** → 第 1 周先做复制/写入/读取/等算最小 PoC，校准轮询阈值；PoC 不通过则整条链路需改方案。
- **业务方配合接口区与 ~34 条桥接公式** → 尽早对齐字段清单与单元格地址；接口区结构固定、业务不移动。
- **轮询 3s/10s 可能偏紧** → 阈值 Nacos 可配，以 PoC 实测校准。
- **平台身份 header 未定** → 字段名可配（Nacos/env），先用默认占位值联调；平台约定后零改码切换。header 缺失有可配降级策略，避免阻塞开发。
- **参数字典正确性** → 72 行按 F=1+表2 收敛后逐项业务校对，作为数据契约冻结再开发写入。
- **表2 两档收益（2h/4h）公式未定** → 挂账，先留占位与开关，公式确认后补齐。
- **前端框架层借鉴带入冗余** → 只移植设计体系与必要框架写法，避免带入交易业务；以启动自检 + P0 自检清单把关。

## 迁移计划

- **上线步骤**：①新建前端工程（XC 设计体系 + 通用框架层）+ 品牌化，配 `.env` 指向网关 `/ir`，默认落地对话首页；②后端基座（团队统一栈）+ Nacos（test）+ `ir_agent` 建库 + Alembic 迁移 + 平台身份读取中间件（header 字段名可配）；③与平台约定跳转入口 URL 与 header 字段名后联调承接；④飞书 PoC 打通后接执行链路；⑤联调 承接→对话→测算→结果→重算→版本；⑥部署至测试环境，经网关暴露 `/ir`。
- **回滚步骤**：全新独立子应用、独立部署，回滚即下线本服务与前端站点；本系统自有 MySQL、不落地登录态，回滚无外溢影响。
